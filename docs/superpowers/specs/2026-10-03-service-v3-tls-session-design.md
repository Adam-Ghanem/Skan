# Service V3: TLS sessions and encrypted application evidence

## Intent and scope

The user approved the next TLS/HTTPS milestone and requires completed changes
to be pushed to GitHub. Starting baseline: main `0bba0da172f208782e6745f8244df3b84992a058`.
Make service intelligence work inside real TLS 1.2/1.3 sessions. Do not add
vulnerability scanning, scripting, GUI features, or unrelated CLI behavior.

The current TLS probe sends a static ClientHello and passively parses records.
It cannot complete a handshake or decrypt TLS application data. A port number,
certificate name, TLS alert, or two-byte record prefix does not establish HTTPS
or a product version.

## Approach

Use OpenSSL 3.x for cryptography. Keep TCP connection ownership, epoll events,
response limits, and cancellation in `ServiceTcpTransport`. A focused
`TlsSession` wrapper owns OpenSSL state and exposes handshake/read/write
progress: ready, want-read, want-write, closed, or error. Its socket BIO uses
nonblocking recv and `MSG_NOSIGNAL` send; it never changes process signal policy.
OpenSSL errors are interpreted immediately after each SSL operation with an
empty thread error queue. This avoids blocking the existing scanner engine.

The existing TCP ClientHello probe requesting a TLS service/tunnel becomes a
handshake-only attempt. Recognize its structurally bounded ClientHello payload
and explicit TLS rule; do not rely on its name or TCP port. Existing corpus
syntax and bytes remain unchanged. A successful handshake publishes a typed
transport event and negotiated metadata, never cipher bytes to the matcher.

The scheduler retains a generic TLS candidate, then runs the existing configured
fallback probes in fresh TLS sessions. Each connection remains one bounded
probe attempt under the existing budget and timeout. A confirmed TLS endpoint
never receives a plaintext fallback. If the initial handshake fails, configured
plaintext fallbacks can still recover a plaintext service on that port.

Only a structurally valid decrypted HTTP response becomes `https`; other
validated application identities retain their name and gain `tunnel=tls`.
HTTP product/version extraction continues using the existing header/JSON
validators. TLS handshake evidence alone reports `tls` with empty product and
application version. Rejected application framing or a TLS protocol failure
retains transport evidence without publishing the failed application's identity.

## Evidence and naming

After handshake completion, record the negotiated TLS version, selected ALPN,
and bounded leaf certificate metadata. Reuse the existing DER parser for names,
SANs and raw ASN.1 validity times; TLS 1.3 certificates are now available through
OpenSSL. Metadata is observational: certificate chain trust, hostname matching,
and peer authenticity are not claimed. Certificate subjects never supply a
software product/version, and offered ALPN is never reported as selected ALPN.

Offer only `http/1.1`; HTTP/2, HTTP/3 and STARTTLS are outside this slice. An
optional library configuration `tls_server_name` supplies a validated ASCII DNS
name for SNI and the default HTTP Host header. Empty means IP scanning without
SNI. Do not derive SNI from an untrusted certificate or silently add reverse DNS.
No new CLI option is required; document the CLI's default virtual-host limit.

## Bounds and lifecycle

- TLS minimum version: 1.2; maximum: 1.3.
- Certificate chain message: 64 KiB; extracted leaf DER: 48 KiB.
- Total inbound encrypted bytes per connection: 512 KiB.
- Preserve the configured application response cap (default 8192 bytes).
- Preserve per-probe deadlines, concurrency, retry and cancellation policies.
- Clean close-notify can finalize a close-delimited response; abrupt TLS EOF
  cannot finalize an application identity from that response.
- Cancellation during handshake, metadata callbacks or application reads must
  not free an Event/Connection while its callback remains active.
- TLS setup/protocol failures remain explicit and never create fabricated
  negotiated versions, certificate fields or HTTPS identities.

## Build and delivery

Declare `libssl-dev (>= 3.0)` for Debian builds, link OpenSSL after object files,
and align CI/container toolchains and README instructions. Debian runtime
dependencies remain generated by shlibs. Retain all existing build-flavor,
sanitizer, fuzz, corpus, machine-output and package gates.

## Validation

Start with a loopback regression proving the existing engine fails to detect
HTTPS behind a self-signed TLS server. Cover TLS 1.2 and 1.3, IPv4/IPv6,
decrypted HTTP fragmentation, certificate-only TLS, malformed application data,
selected ALPN, SNI, handshake failure, abrupt EOF, response cap, timeout,
concurrency and cancellation. Verify JSON/XML/grepable evidence parity and the
unchanged corpus round trip. Run the full suite, targeted ASan/UBSan, an
independent whole-branch review, and exact-head GitHub CI before integration.
No benchmark superiority or real-world accuracy claim follows from these tests.
